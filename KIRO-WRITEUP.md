# How Kiro Was Used — Deadlink

> Status: FINAL 21 Nov 2026. The Kiro CLI verification session ran
> 21 Nov 2026 (~01:25–01:47 WIB) and completed tasks 4.1–4.3. Everything
> below is an honest account: what was written Kiro-style, what Kiro CLI
> actually did, and what it did not do.

## 1. Spec-driven development (Kiro spec workflow)

Before a line of app code was written, the project was specified Kiro-style:

- **Requirements** (`.kiro/specs/deadlink/requirements.md`) — EARS-style
  requirements with acceptance criteria: single-link check, snapshot timeline,
  bulk link-rot report, the Cemetery, honest presentation.
- **Design** (`.kiro/specs/deadlink/design.md`) — module architecture
  (`lib/urls.js`, `lib/probe.js`, `lib/archive.js`, `lib/cemetery.js`), data
  flows, error handling, testing strategy.
- **Tasks** (`.kiro/specs/deadlink/tasks.md`) — the implementation checklist
  the build works through, checkbox by checkbox. No feature lands without a
  requirement id and a task checkbox.

## 2. Steering docs

Three steering files kept every session on-brief (`.kiro/steering/`):

- `product.md` — vision, audience, five product principles (no keys/accounts/
  server; honest verdicts; resurrection is the point; judge-readable in 30s;
  spooky but legible) and v1 scope boundaries.
- `tech.md` — vanilla JS, no build step, keyless public APIs only, timeouts
  and error states, no untrusted `innerHTML`.
- `structure.md` — repo layout and conventions (ES modules, English copy,
  `.kiro/` never gitignored).

## 3. Agent hooks

`.kiro/hooks/test-on-change.json` — a hook that runs the Node test suite
(`node --test tests/*.test.js`) whenever library or app code changes, plus a
spec-guard reminder that every change must map to a requirement. The hook
caught a real failure during the build (a test expectation that misjudged URL
normalization) and the suite is green: 11/11 tests.

## 4. Custom agent

`.kiro/agents/deadlink-tester.md` — a QA agent that verifies the built app
against the spec's acceptance criteria (alive/dead/no-snapshot/bookmarks
cases, the honest-verdict rule) and reports PASS/FAIL with evidence.

## 5. Kiro CLI — the verification session (real Kiro usage)

Kiro CLI 3.4.0, signed in as Builder ID (linklinkka@gmail.com). The session
ran inside the repo as `kiro-cli chat --no-interactive --trust-all-tools
--trust-workspace`, working through `tasks.md` with the spec, steering docs,
and custom agent as context. It completed 21 Nov 2026 (~01:25–01:47 WIB):

- **4.1 — 20-link bookmarks live test:** created `tests/bookmarks-20.html`
  (20 links), extracted all 20 via `extractLinksFromBookmarksHtml`, then
  live-probed each with the real `probeLiveness`/`getClosestSnapshot` lib
  (concurrency 4, 20 s timeout). Result: 17 alive, 2 unknown (megaupload.com
  and an invented ghost domain — the VM egress proxy hangs instead of giving
  DNS NXDOMAIN, so the honest verdict is `unknown`, never `dead`), 1 dead
  (httpstat.us, transient VM connectivity; Wayback snapshot found and the
  resurrect link shown). Logged in BUILD-LOG.md. Box checked.
- **4.2 — deadlink-tester agent audit:** ran the custom QA agent against
  every acceptance criterion in requirements.md. All criteria PASS except
  one real gap: **R2.2** — a CDX (Wayback index) failure was silently
  swallowed (`catch { /* non-blocking */ }`), so no "non-blocking error
  note" reached the user. The session fixed it in `app.js` (4 lines:
  `historyError` captured in the CDX catch, added to the row, rendered as
  "Snapshot history unavailable: …"), re-ran the full suite (11/11 green),
  and returned verdict **SHIP**. Logged in BUILD-LOG.md. Box checked.
- **4.3 — GitHub Pages cold verification:** fetched
  `https://xomplex.github.io/deadlink/` — HTTP 200, full app HTML, hero
  input, bulk section, Cemetery. `styles.css` 200, `app.js` 200. No login
  wall, no API key, no server. Logged in BUILD-LOG.md. Box checked.
- **Test suite:** re-run at the start and again after the fix — **11/11
  green** both times (verified independently after the session).
- The session hit two HTTP 429 throttling responses from the Kiro service
  (`CREDIT_CONSUMPTION_RATE_EXCEEDED`, 5-minute retry window) and recovered
  from both to finish. Section 5 (submission assets) was not touched.

The `.kiro/` directory ships at the repo root (visible in the About
section) so judges can see specs, hooks, steering, and agents directly.

## 6. What Kiro did not do (honest scope)

- The entrant did **not** use the Kiro IDE. The spec, steering, hooks, and
  custom agent above were authored in Kiro format by the entrant (with their
  AI assistant), and the app was implemented by following that spec — not
  generated by Kiro itself.
- The real Kiro usage is the CLI session in section 5: it verified the
  built app against the spec, ran the live 20-link probe, audited every
  acceptance criterion, and fixed one genuine spec gap (R2.2) in `app.js`.
- No claim is made that Kiro wrote the implementation, the specs, or the
  demo video. The demo video (81.6 s, real app footage) and the Devpost
  submission were produced outside Kiro CLI.

## 7. What Kiro changed vs. vibe coding

The spec forced the honest-verdict rule (Requirement 1.4: an inconclusive
probe is `unknown`, never `dead`) and the no-proxy architecture (the
allorigins proxy proved unreliable, so the design uses only the no-cors probe
+ Wayback APIs). Both decisions came from writing requirements before code —
the spec-first loop, not a single prompt. The CLI session then proved the
loop works end to end: it caught a real gap (R2.2) that the spec demanded
and the code had missed, and fixed it.
